## What is SPI?

**SPI (Serial Peripheral Interface)** is a **high-speed, full-duplex, synchronous** serial protocol. It is the usual way a microcontroller talks to displays, TF/SD cards, Flash memory and sensors.

Its defining traits:

- **Four-wire** — four signal lines (can drop to three when there is only one slave).
- **Master–slave** — the master owns the clock and decides when each transfer happens; slaves never talk unless selected.
- **Full-duplex** — data can travel in both directions at the same time (unlike UART's shared timeline or I2C's one-wire-at-a-time bus).
- **Synchronous** — the master generates the clock, so no baud rate has to be agreed on in advance.
- **Fast** — typically tens of MHz, much faster than I2C or UART.

### The four signal lines

| Signal | Full name | Direction | Purpose |
| --- | --- | --- | --- |
| **SCK** | Serial Clock | Master → Slave | Clock generated by the master; latches every bit on both sides |
| **MOSI** | Master Out Slave In | Master → Slave | Data sent from the master to the slave |
| **MISO** | Master In Slave Out | Slave → Master | Data returned from the slave to the master |
| **SS / CS** | Slave Select / Chip Select | Master → Slave | Active **low**: the master pulls one CS low to talk to that particular slave |

```
        SCK ─────────┬──────────────┬──────────────┬───
        MOSI ────────┼──────────────┼──────────────┼───
        MISO ────────┼──────────────┼──────────────┼───
                     │              │              │
               ┌─────┴─────┐  ┌─────┴─────┐  ┌─────┴─────┐
               │  Slave 1  │  │  Slave 2  │  │  Slave 3  │
               │    CS1    │  │    CS2    │  │    CS3    │
               └───────────┘  └───────────┘  └───────────┘
   Master: SCK, MOSI, MISO  shared by everyone
           CS1, CS2, CS3    one dedicated pin per slave
```

Key points:

- **SCK, MOSI and MISO are shared** — every slave listens to the same three wires.
- **CS is unique per slave** — the master selects who it talks to by pulling that slave's CS low. Each extra slave costs one more GPIO.
- Some write the names as SCLK/COPI/CIPO; OSHWA has a [resolution to redefine SPI signal names](https://oshwa.org/resources/a-resolution-to-redefine-spi-signal-names/).

### SPI on the ESP32

ESP32 chips carry several SPI controllers:

| Controller | Typical role |
| --- | --- |
| **SPI0 / SPI1** | Reserved for accessing **Flash / PSRAM** — don't use them for your own devices |
| **SPI2 / SPI3** | **General-purpose** buses you are free to use, with flexible pin assignment |

In Arduino you get them through the `SPI.h` library:

| Object | Bus | Notes |
| --- | --- | --- |
| `SPI` | Hardware **SPI2** (a.k.a. **FSPI**) | The default, pre-created object — "F" stands for *Fast*, **not** *Flash* |
| `SPIClass hspi(HSPI)` | Hardware **SPI3** | A second, independent bus object you create yourself |

Two things worth remembering:

- **`SPI.begin(sck, miso, mosi, cs)`** — with no pins it uses the bus's default pins; with explicit pins it **routes through the GPIO matrix**, so almost any free GPIO works.
- **Avoid occupied pins** — USB, the onboard LED and Flash-related pins are already taken; check your board's pinout before choosing.

## Example 1: Driving an OLED over SPI

The sketch in [`SPI_Communication.ino`](SPI_Communication.ino) drives a **Waveshare 1.5inch OLED module** (SSD1327 controller) over SPI and draws text on it. SPI displays refresh noticeably faster than their I2C versions.

### Components

1× [Waveshare 1.5inch OLED Module](https://www.waveshare.com/1.5inch-oled-module.htm), 1× breadboard, jumper wires, ESP32-S3-Zero board.

### Wiring

| OLED module pin | ESP32-S3-Zero pin | Purpose |
| --- | --- | --- |
| SCK | **GPIO13** | SPI clock |
| MOSI | **GPIO11** | SPI data output (master → display) |
| CS | **GPIO10** | Chip select |
| DC | **GPIO8** | Data/command select |
| VCC | **3.3V** | Power |
| GND | **GND** | Ground |

> This display is write-only from the MCU's point of view, so **MISO is not connected** — that's why the code passes `-1` for it.

### Required library

The sketch depends on the **Adafruit SSD1327** library. In the Arduino IDE open **Tools → Manage Libraries…** and search for `Adafruit SSD1327`, then install it (it will pull in *Adafruit GFX Library* as a dependency).

### Code

```cpp
#include <SPI.h>
#include <Adafruit_SSD1327.h>

#define OLED_SCK 13    // Clock cable
#define OLED_MOSI 11   // Data output line
#define OLED_CS 10     // Chip select line

#define OLED_DC 8      // Data/command select line
#define OLED_RESET -1  // Reset pin (unused)

// Create a display object
Adafruit_SSD1327 display(128, 128, &SPI, OLED_DC, OLED_RESET, OLED_CS);

void setup() {

  Serial.begin(9600);

  // Initialize SPI bus
  SPI.begin(OLED_SCK, -1, OLED_MOSI, OLED_CS);

  Serial.println("SSD1327 OLED test");

  // Initialize the display
  if (!display.begin()) {
    Serial.println("Unable to initialize OLED");
    while (1) yield();
  }

  // Display settings
  display.clearDisplay();
  display.setRotation(3);
  display.setTextSize(2);
  display.setTextColor(SSD1327_WHITE);

  // Display text
  display.setCursor(10, 10);
  display.println("Hello,");
  display.setCursor(40, 30);
  display.setTextColor(SSD1327_BLACK, SSD1327_WHITE);
  display.println(" World!");
  display.display();
  display.setCursor(15, 60);
  display.setTextColor(SSD1327_WHITE);
  display.println("SPI TEST");
  display.display();

  delay(1000);
}

void loop() {
}
```

### How it works

1. **`#include <SPI.h>`** — Arduino's SPI library; gives you the `SPI` bus object and `SPI.begin()`.
2. **`SPI.begin(OLED_SCK, -1, OLED_MOSI, OLED_CS)`** — initialises the bus and assigns the pins:
   - `OLED_SCK` — clock line
   - `-1` — **MISO is unused** (the display only receives)
   - `OLED_MOSI` — data out
   - `OLED_CS` — chip select
   Because explicit pins are given, they are routed through the **GPIO matrix** rather than the fixed default pins.
3. **`Adafruit_SSD1327 display(128, 128, &SPI, OLED_DC, OLED_RESET, OLED_CS)`** — creates the display object:
   - `128, 128` — resolution
   - `&SPI` — use the default SPI bus object (SPI2/FSPI)
   - `OLED_DC`, `OLED_RESET`, `OLED_CS` — the control pins; `OLED_RESET -1` means "no reset line is wired".
4. **`display.begin()`** — resets and probes the panel over SPI. If it fails the sketch halts and prints `Unable to initialize OLED` to the Serial Monitor — a quick way to spot a wiring or power problem.
5. **The DC pin** — SPI itself has no idea what a "command" is. Displays therefore add a **D/C line**: low = command byte, high = data byte. It is the one extra wire SPI displays need beyond the four SPI signals.
6. **`display.setRotation(3)` / `setTextSize()` / `setTextColor()`** — configure orientation and font before drawing.
7. **`display.display()`** — the library builds the frame in RAM first; this call pushes the buffer out over SPI to the panel. Text drawn without it never appears.
8. **`SSD1327_BLACK, SSD1327_WHITE`** — the two-argument form sets foreground *and* background colour, which is what produces the inverted `World!` badge.

### Running result

1. Upload the sketch and watch the OLED:
   - line 1: `Hello,` in white
   - line 2: `World!` **inverted** (black text on a white block)
   - line 3: `SPI TEST` in white
2. Open the Serial Monitor — it prints `SSD1327 OLED test`, then `Unable to initialize OLED` if the display is not detected.

## Example 2: Using a Second SPI Bus (multiple devices)

The ESP32 exposes more than one general-purpose SPI controller, so a second peripheral can live on its own bus with its own pins:

```cpp
#include <SPI.h>

SPIClass hspi(HSPI);   // create a second bus object on hardware SPI3

void setup() {
  // Initialize the HSPI bus and specify its pins
  hspi.begin(HSPI_SCLK, HSPI_MISO, HSPI_MOSI, HSPI_CS);

  // ...
}

void loop() {
  // ...
}
```

Notes:

- **`SPI` already exists** — it is pre-created by the library. Any *additional* controller (here `HSPI` → hardware SPI3) needs its own `SPIClass` object.
- **`hspi.begin(sck, miso, mosi, cs)`** works exactly like `SPI.begin(...)`, but on the second bus, so the two peripherals never fight over pins or timing.
- **You don't need a second bus for multiple devices** — on a *single* bus, each slave just gets its own CS line and you assert the right one before each transfer. A second bus is for separating traffic (e.g. a display on one, an SD card on the other) or when you've run out of convenient pins.

## Troubleshooting

- **`Unable to initialize OLED`** — check VCC/GND (3.3V, **not** 5V), SCK→GPIO13, MOSI→GPIO11, CS→GPIO10 and DC→GPIO8. Also confirm the Adafruit SSD1327 library is installed.
- **Screen stays blank but init succeeds** — you probably forgot `display.display()`, or drew before setting a rotation/colour that matches the panel.
- **Garbled or partial image** — re-seat the jumper wires; long breadboard jumpers are the usual culprit at SPI speeds. Try shorter wires, or lower the bus frequency in `display.begin(...)`.
- **Pins clash with USB / the onboard LED** — GPIO matrix routing lets you move SCK, MOSI, CS and DC to any free GPIO; just update the `#define`s and the wiring together.
- **Wrong text orientation** — change `display.setRotation()` (0–3); `3` suits this module mounted as wired in the tutorial.

## Ideas to extend it

- Animate the display — draw a counter or a scrolling waveform in `loop()` instead of drawing once in `setup()`.
- Add a second slave (another display or a sensor) on the **same** bus with its own CS pin, and demonstrate selecting between them.
- Wire up the unused **MISO** line and read from a device that actually replies (an SD card is the classic case).
- Move the display to the second bus (`SPIClass hspi(HSPI)`) to free the default `SPI` bus for something else.
- Compare refresh speed against the same content on I2C to see why SPI is preferred for graphics.
